# Нормализация — полный пересчёт по границе `newest_fetched_id`

Нормализатор не ведёт очередь обработанных сообщений. Каждый раз, когда вырос `newest_fetched_id`, он заново строит все посты и статьи из блоков `raw_posts` с `message_id <= newest_fetched_id` и одной транзакцией заменяет содержимое `posts` и `articles`. Пересчёт дешёвый: разбор HTML всех 44 тыс. блоков на Rust занимает 2,6 с ([анализ](../research/briefly-normalization-analysis.md#время-полного-пересчёта)), а части составной статьи склеиваются только когда видны все сохранённые блоки сразу.

Граница `newest_fetched_id` — наибольший ID, ниже которого загрузчик сохранил всё без пропусков. Блоки выше неё — недокачанный текущий проход, который идёт от свежих к старым. Если такие блоки игнорировать, данные для нормализатора только дописываются сверху: более ранняя часть статьи никогда не появляется после более поздней. Поэтому ID статьи — `message_id` её первой части — стабилен между пересчётами. Меняется он только при смене правил склейки.

## Considered Options

- **Инкрементальная очередь** (`processed_at`, выборка `FOR UPDATE`, повторная оценка затронутых статей, advisory-блокировка против отдельной пересборки; [заметка](../research/postgres-normalization-queue.md)). Отвергнута: при пересчёте за секунды её сложность ничего не даёт, а смена правил всё равно требует полной пересборки.
- **UUIDv7 или хэш состава как ID статьи** ([заметка](../research/uuidv7-article-identity.md)). Были нужны, чтобы пережить обратную загрузку истории. При границе `newest_fetched_id` нормализатор её не видит, и хватает `message_id` первой части, который заодно ведёт на `t.me/<канал>/<ID>`.
- **Нормализовать всё сохранённое, включая недокачанный проход.** Отвергнуто: во время первого прохода части 2 и 3 появляются раньше части 1, и статьи с их ID менялись бы на каждом пересчёте.

## Consequences

- Пока первый проход не завершён (`newest_fetched_id IS NULL`), постов и статей нет. Свежие публикации появляются после завершения очередного прохода.
- Время пересчёта растёт линейно с историей. Если оно станет заметным, сначала стоит кэшировать разбор HTML, а не возвращать очередь.
- Отдельного действия «пересобрать» нет: пересчёт при старте процесса применяет новые правила после деплоя.
