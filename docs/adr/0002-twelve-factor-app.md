# Приложение следует 12-factor

Загрузчик, веб-сервер и будущие процессы строятся по [12-factor app](https://12factor.net/ru/): процессы одноразовы и не хранят состояния, конфигурация задаётся только окружением, а всё долговременное состояние — сообщения, курсоры, паузы Telegram и сама сессия Telegram — живёт в PostgreSQL как подключаемом сервисе. Так любой процесс можно остановить, перезапустить или перенести на другую машину, имея только бинарник, переменные окружения и доступ к БД. Соответствие по каждому фактору расписано в [плане](../scraper-plan.md#5-эксплуатация-12-factor).

## Consequences

- Сессия Telegram хранится в PostgreSQL, а не файлом на диске: процесс без локального состояния. Для этого нужна собственная реализация хранилища сессии `grammers-session`.
- Миграции и первый вход в аккаунт Telegram — разовые административные команды того же бинарника (`migrate`, `login`) с той же конфигурацией. Долгоживущие процессы схему не меняют и интерактивно не авторизуются.
- Загрузчик — тип процесса с ровно одним экземпляром: одна сессия Telegram и вывод состояния прохода из БД рассчитаны на одного писателя. Второй экземпляр должен обнаружить первый и завершиться, а не масштабироваться.
- Логи пишутся только в stdout как поток событий; файлов логов приложение не ведёт. Состояние для веб-админки хранится в БД, а не выводится из логов.
