# Часть 2. Нормализатор

Нормализатор строит из сохранённых **блоков веб-ленты** **посты** и **статьи** — единицы будущего поиска. Термины — по [глоссарию](../CONTEXT.md). Устройство — полный пересчёт по границе `newest_fetched_id` ([ADR-0004](adr/0004-normalization-full-recompute.md)). Правила выведены из [анализа загруженной истории](research/briefly-normalization-analysis.md); цифры и примеры ниже — оттуда. Поиск на Tantivy — следующая поставка, здесь он не реализуется.

## 1. Вход

- Нормализатор читает только блоки `raw_posts` с `message_id <= newest_fetched_id`: ниже этой границы загрузчик сохранил всё без пропусков ([план загрузчика](scraper-plan.md#1-получение-сообщений)). Пока `newest_fetched_id IS NULL` (первый проход не завершён), пересчёт даёт пустой результат.
- Каждый блок разбирается по `payload_schema` в представление, не зависящее от источника: ID, дата публикации, тип (текст, фото, видео, альбом, опрос, служебное), ID элементов альбома, видимый текст, ID сообщения, на которое блок отвечает (reply), и источник пересылки. Видимый текст — текст блока с переводами строк вместо `<br>`, без адресов ссылок, без текста ссылочного превью и цитаты ответа. Разбор `t.me/s html v1` живёт рядом с источником веб-ленты; будущий MTProto добавит свою реализацию.
- Неизвестная `payload_schema` или блок, который не удалось разобрать, — ошибка пересчёта: результат прошлого пересчёта остаётся, ошибка видна в админке.

## 2. Правила

### Посты

Пост образует блок с непустым видимым текстом: текстовое сообщение, фото или видео с подписью, альбом, пересланное из другого канала (источник пересылки сохраняется). Служебные сообщения, опросы и блоки без текста постов не образуют.

### Части составной статьи

**Маркер части** ищется в первой строке текста (заголовке); берётся последний маркер, начинающийся в первых 400 символах, с номером от 1 до 30. Формы: `Часть N/M`, `Часть N.`, `Часть N:`, `(часть N)`, `…, часть N/M.`, без учёта регистра; в истории встречаются `Часть` и `часть`. **Заголовок** — текст первой строки до маркера. Текст после маркера в той же строке (`Лоуренс Фридман (часть 2): Именно вопрос…`) — уже содержание.

Слово «часть» с числом в теле статьи маркером не бывает: остальные строки не сканируются. Риск остаётся у одиночных постов, где весь текст — один абзац, поэтому маркер — законченная конструкция, а не «часть» с числом посреди фразы. Ложные маркеры отсекаются так:
- после номера идёт общее число через `/`, `\` или `//` (`Часть 1\3`, `Часть 1//2` встречаются), либо `.`, `:`, `)`, либо конец строки. «Часть 3 бюджета» — не маркер. На срезе анализа это условие не потеряло ни одного настоящего маркера;
- слово только «часть» в единственном числе: «части N» в заголовках означает другое («большей части 26 июля», «части 10-го корпуса», «Части 1-10»);
- за номером не идут дефис или буква: «ключевую часть 21-го пакета» — не маркер;
- номер не больше 30: «оставшуюся часть 2023 года» — не маркер.

Посты с маркером обрабатываются по возрастанию `message_id`. Пост с номером `n > 1` присоединяется к последней **открытой** статье, у которой:

1. номер последней части — `n − 1`;
2. последняя часть опубликована не более чем за 24 ч до этого поста;
3. сходство нормализованных заголовков не ниже 0,6. Нормализация: нижний регистр, `ё → е`, без кавычек `«»"“”„'`, `*` и прочей пунктуации, пробелы схлопнуты. Сходство — доля совпадающих символов по алгоритму Ratcliff/Obershelp (как `difflib.SequenceMatcher.ratio`).

Исправление опечаток редакции:

- **Повтор номера.** Пост с номером, равным номеру последней части подходящей статьи, опубликованный не позже 3 ч после неё, считается следующей частью. В анализе все 15 таких пар — опечатки.
- **Конфликт общего числа** (`1/4`, `2/3`, `3/3`): статья принимает наибольшее объявленное число.
- **Первая часть без маркера.** Если пост с номером 2 не нашёл статью, но отвечает (reply) на пост без маркера, этот пост становится частью 1 новой статьи с заголовком части 2.

Пост с маркером, который никуда не присоединился, открывает новую статью — даже если его номер больше 1. Части разных **повторных публикаций** и выпусков ежедневных рубрик с одинаковым заголовком разделяет окно 24 ч. По одной близости ID или темы, без маркера и без reply, посты не склеиваются. Пост без маркера образует **одиночную** статью.

Номер части в статье — порядковый после исправления опечаток (1, 2, 3…), а не номер из текста.

### Статус и текст статьи

| Статус | Когда |
| --- | --- |
| `single` | одиночная статья — один пост без маркера |
| `complete` | составная: части 1…k подряд и k не меньше объявленного общего числа (если оно есть) |
| `incomplete` | составная: пропуск в номерах, нет части 1, частей меньше объявленного общего числа или единственная часть без объявленного общего числа (продолжение ожидалось, но его нет) |

**Текст для поиска:** заголовок один раз, затем тексты частей по порядку. Из каждой части убираются маркер части (у составных — вся первая строка с заголовком) и **концовка** — последняя строка, совпадающая с известным списком: `Подписаться.`, `Подписаться`, `Подписаться | Сайт | Х` и варианты пробелов и `|` вокруг них, `Подпишись на Briefly и RTVI`, `@brieflyru`, `@rusbri`, `Подпишись.`, `Подписывайтесь на NEWS.ru`, `Подпишись на RTVI в Telegram | MAX`, `Подпишись на RTVI в Telegram | МАКС`. Неизвестная последняя строка остаётся в тексте: лучше лишний хвост, чем вырезанное содержание. Список пополняется по наблюдениям, повторная загрузка не нужна.

У одиночной статьи заголовка нет: выдача поиска покажет начало текста.

## 3. Хранилище

Миграция части 2 добавляется в тот же crate хранилища, в общую линейную историю.

| Таблица | Назначение и ключевые поля |
| --- | --- |
| `articles` | `id BIGINT` PK, FK к `raw_posts` — `message_id` первой части; `title TEXT NULL` — только у составных; `search_text TEXT NOT NULL`; `status TEXT NOT NULL` — `single`/`complete`/`incomplete`; `declared_parts INT NULL` — объявленное общее число; `published_at TIMESTAMPTZ NOT NULL` — дата первой части. |
| `posts` | `message_id BIGINT` PK, FK к `raw_posts`; `article_id BIGINT NOT NULL` FK к `articles`; `part_no INT NULL` — порядковый номер в составной статье; `text TEXT NOT NULL` — видимый текст без концовки; `published_at TIMESTAMPTZ NOT NULL`; `forwarded_from TEXT NULL`. |
| `normalizer_state` | Единственная запись: `normalized_up_to BIGINT NULL` — `newest_fetched_id`, по которому построен текущий результат; время начала и длительность последнего пересчёта; последний heartbeat; текст и время последней ошибки. Секреты и `payload` сюда не записывать. |

Пересчёт — одна транзакция: `TRUNCATE posts, articles`, вставка нового результата, обновление `normalizer_state`. Читатели видят либо прежний результат, либо новый. `raw_posts` нормализатор не меняет.

## 4. Процесс

- Новый тип процесса — команда `normalizer`, ровно один экземпляр: session-level advisory-блокировка PostgreSQL с отдельным от загрузчика ключом, второй экземпляр завершается с понятной ошибкой. Остановка по сигналу — как у загрузчика: текущая транзакция откатывается или завершается.
- При старте выполняется пересчёт: так новые правила применяются после деплоя без отдельного действия. Затем процесс раз в `NORMALIZER_POLL_INTERVAL_SECS` (по умолчанию 30) сравнивает `newest_fetched_id` с `normalized_up_to` и пересчитывает, если граница выросла.
- Ошибка пересчёта записывается в `normalizer_state`; следующая попытка — на следующем опросе. Результат прошлого пересчёта остаётся.
- Загрузчик и нормализатор не знают друг о друге: связь только через `ingestion_state.newest_fetched_id`.

## 5. Веб-админка

Блок «Нормализатор» на той же странице, тем же способом (HTMX-фрагмент сводки, только чтение):

- heartbeat и последняя ошибка;
- `normalized_up_to` и отставание от `newest_fetched_id`;
- время и длительность последнего пересчёта;
- число постов; число статей по статусам; число блоков до границы, не ставших постами;
- последние 20 неполных статей со ссылками `t.me/<канал>/<ID>` на части — чтобы видеть ошибки правил на живых данных.

Управляющих действий нет: отдельная пересборка не нужна ([ADR-0004](adr/0004-normalization-full-recompute.md)).

## 6. Границы Rust-проекта

- **`telegram`** — разбор блока по `payload_schema` в представление из раздела 1 (рядом с источником веб-ленты, тем же `scraper`).
- **`normalizer`** (новый crate) — правила раздела 2 как чистая функция «разобранные блоки → посты и статьи». Без БД, HTML и асинхронности.
- **`storage`** — миграция, чтение блоков до границы, замена результата одной транзакцией, `normalizer_state`, сводка для админки. Остаётся единственным crate, который обращается к БД.
- **`app`** — команда `normalizer`, цикл опроса, конфигурация, блок админки.

## 7. Тесты

- **Golden-тесты правил** в crate `normalizer` на реальных блоках из [кандидатов в фикстуры](research/briefly-normalization-analysis.md#кандидаты-в-фикстуры). HTML этих блоков выгружается из БД в `tests/fixtures/`; для каждого случая ожидаемый результат — состав статей, номера частей, статус, заголовок и текст для поиска.
- **Тесты разбора** в crate `telegram`: текст с `<br>` и ссылками, альбом с вложенными текстовыми `div`, ответ (reply), пересланное, служебное, опрос, ссылочное превью.
- **Тесты хранилища и процесса** на `#[sqlx::test]`: граница `newest_fetched_id` (блоки выше не попадают в результат, `NULL` даёт пустой результат), атомарная замена, пересчёт только при росте границы, ошибка пересчёта сохраняет прежний результат, второй экземпляр завершается.
- **Сводный прогон по полному дампу** — вне репозитория, по флагу или переменной окружения с путём к дампу. Печатает число постов, статей по статусам и аномалий и время пересчёта; ловит регрессии правил, которые не видны на фикстурах. Ориентир на срезе анализа: ~4 600 составных статей, неполных — десятки.

## Порядок реализации

Вертикальные срезы, каждый — отдельный тикет:

1. **Разбор блока** в crate `telegram` и тесты разбора.
2. **Правила** в crate `normalizer`: фикстуры, golden-тесты, сводный прогон по дампу.
3. **Схема и процесс**: миграция, `storage`, команда `normalizer`, тесты на `#[sqlx::test]`. Проверка на реальной БД: после запуска число статей и статусов совпадает со сводным прогоном.
4. **Блок в админке.**

## Отложено

- **Поиск на Tantivy** по `articles.search_text`: индекс, ранжирование, морфология русского языка, страница поиска. Индекс при каждом пересчёте можно перестраивать целиком (секунды на ~40 тыс. документов) — решить в своей поставке.
- **ML для склейки** (например, эмбеддинги заголовков). Не нужно: правила оставляют ~100 аномалий на ~4 600 статей, а детерминизм нужен для golden-тестов. Вернуться, если на живых данных всплывут ошибки, которые правилами не закрыть.
- **Журнал событий воркеров** (`worker_events`). Пока хватает последней ошибки, как у загрузчика.
