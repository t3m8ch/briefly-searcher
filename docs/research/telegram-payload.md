# Telegram message payload: what can “as returned, but text” mean?

The API `Message` is a **typed TL value**, not plain post text: its `message:string` field contains the post text/caption, while optional `entities` describe formatting, `media` describes an attachment, and `peer_id`, `id`, `date`, `reply_to`, `grouped_id`, etc. carry context. The boxed `Message` type also has `messageEmpty` (nonexistent) and `messageService` (service event) variants. A media-only post need not provide useful `message` text; excluding downloads is different from excluding `media` *metadata*. Decide whether “text only” means **no downloaded files**, **no media metadata in the stored representation**, or **only the `message` string**; the last two choices cannot preserve the complete API object. [Message constructor](https://core.telegram.org/constructor/message), [Message variants](https://core.telegram.org/type/Message), [file/document metadata](https://core.telegram.org/constructor/messageMediaDocument).

| Textual representation | Preserves | Loses / tradeoff |
| --- | --- | --- |
| Exact received TL object bytes encoded as **base64 or hex** | Byte-for-byte *selected captured byte slice* after decoding; encoding is reversible. | Opaque for textual research; full TL object may include media metadata/embedded binary fields; requires capturing the original object boundaries **before** deserialization, not serializing it again. Decoder needs the applicable TL constructor/schema and its boxed/bare context. This does **not** imply storing MTProto transport framing, session identifiers, encrypted packets, or gzip wrapper unless those bytes are deliberately selected as the capture boundary. [TL serialization](https://core.telegram.org/mtproto/serialize), [MTProto envelope](https://core.telegram.org/mtproto/description), [gzip-packed responses](https://core.telegram.org/api/invoking#data-compression) |

Pin/record generating schema layer for later interpretation. | Typed **JSON** of selected fields or full decoded object | Legible, queryable records; can explicitly retain original `message` Unicode text, entity offsets/types, ID, date, replies and album ID while omitting media metadata. Crate example: `grammers-tl-types` offers optional `impl-serde` (not enabled by default). | A projection omits fields by design; full JSON is still a library/schema-specific mapping, **not Telegram's original TL bytes**. Define retained fields and representation/version explicitly rather than assume future round-trip. [message fields](https://core.telegram.org/constructor/message), [crate features](https://docs.rs/grammers-tl-types/latest/grammers_tl_types/) |
| Rust **Debug** rendering | Quick human inspection (`impl-debug` is a default feature of `grammers-tl-types`). | Debug is a diagnostic rendering, not a documented stable interchange or reversible TL encoding; unsuitable as the sole archival form. | Only `message` UTF-8 text | Smallest directly readable research corpus (and captions). | Drops identity, timestamps, styled-text entities, explicit album/reply links and attachment metadata; cannot later recover them from prose alone. [message fields](https://core.telegram.org/constructor/message), [styled-text entities](https://core.telegram.org/api/entities) |

**Identity and grouping.** `message.id:int` identifies a channel post in the context of `message.peer_id`; store the channel identity with that ID, not an ID alone. Do **not** confuse it with the transport-level `msg_id:long`, which identifies a time-dependent MTProto packet *within a session*. [message fields](https://core.telegram.org/constructor/message), [channel-specific message ID sequences](https://core.telegram.org/api/updates#message-id-sequences), [transport msg_id](https://core.telegram.org/mtproto/description#message-identifier-msg-id). The optional `grouped_id:long` explicitly links messages in one **album/media group** sent with `messages.sendMultiMedia`; captions may differ per media item. `reply_to.reply_to_msg_id` and `reply_to.reply_to_top_id` explicitly link replies/threads, not necessarily successive editorial parts of one article. No documented `Message` field here declares a generic multi-post **article** boundary; adjacent IDs/time or matching layout would be heuristics, not protocol guarantees. [grouped_id](https://core.telegram.org/constructor/message#parameters), [albums and per-file captions](https://core.telegram.org/api/files#albums-grouped-media), [reply header](https://core.telegram.org/constructor/messageReplyHeader).

**Stability and capture boundary.** TL values have binary constructor identifiers and conditional fields; boxed types include a constructor number and bare types omit it where the containing schema supplies the type. Telegram versions API constructors/methods through numbered layers because changing a declaration may change its constructor number, and documents cases where older-layer constructors can arrive on a newer-layer connection. Therefore a base64 TL object is trivial to **preserve as bytes**, but not schema-free or guaranteed decodable forever with only a future *current* schema; record the layer/decoder version and whether bytes represent a boxed `Message` or a segment inside an enclosing response. For exact *received* bytes, select/capture that segment at the raw response boundary; a high-level typed API alone cannot establish exact-byte provenance. [TL serialization](https://core.telegram.org/mtproto/serialize#boxed-and-bare-types), [layer behavior](https://core.telegram.org/api/invoking#layers), [crate LAYER](https://docs.rs/grammers-tl-types/latest/grammers_tl_types/).

**Decision to grill:** Is “as Telegram returned” an archival **exact-byte** requirement (then capture TL bytes and accept included metadata plus version/capture complexity), or an archival **semantic text/metadata** requirement (then define a JSON field projection including identifiers/group cues)? Neither raw TL bytes nor the entire decoded object meets “no media metadata”; plain post text does not preserve grouping cues. [Message fields](https://core.telegram.org/constructor/message), [TL serialization](https://core.telegram.org/mtproto/serialize).
