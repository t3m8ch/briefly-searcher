# Telegram channel history: official API findings

Scope: a historical and ongoing, text-only scan of the public channel `@brieflyru`; edits and deletions are **not** to be tracked. This note does not select a library, login flow, or credential source.

## Bot API versus MTProto

- **Bot API cannot perform a full historical scan.** Its `getUpdates`/webhook endpoints deliver the bot's incoming updates, not an arbitrary channel-history listing; pending updates are retained for **at most 24 hours**. The Bot FAQ says a bot receives channel messages where it is a member, and the `Update` schema includes `channel_post` and `edited_channel_post`. Bot API `getUpdates.offset` is an **update ID**, not a channel message ID or historical pagination cursor. Neither a local Bot API server nor bot membership replays 43k older posts. [Bot API: getting updates, Update, getUpdates](https://core.telegram.org/bots/api#getting-updates); [Bot FAQ: messages received](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get); [Bot API: local server features](https://core.telegram.org/bots/api#using-a-local-bot-api-server).
- **MTProto provides a documented history route:** [`messages.getHistory`](https://core.telegram.org/method/messages.getHistory) returns a peer's history in descending date order and explicitly says **only users can use this method** (an MTProto bot authorization is insufficient). Its `peer` is an `InputPeer`; [`contacts.resolveUsername`](https://core.telegram.org/method/contacts.resolveUsername) resolves `@brieflyru` to peer information, and [`inputPeerChannel`](https://core.telegram.org/constructor/inputPeerChannel) takes the channel ID and access hash. Telegram advises retaining the peer/access hash rather than repeatedly resolving it; access hashes are tied to the login authorization and cannot be blindly shared between authorizations. [Peer database](https://core.telegram.org/api/peers#access-hash).

## Retrieval and continuation

- An initial `messages.getHistory(peer, offset_id=0, offset_date=0, add_offset=0, limit=100, max_id=0, min_id=0, hash=0)` is a **pagination sketch**, not a promised per-call size: Telegram documents typical limits of **1–100** and method-specific behavior. For older pages, take the oldest returned message ID as `offset_id`, keep `add_offset=0`, and repeat; Telegram's explicit example says this fetches messages *older than* the anchor. Check actual returned messages and stop at exhausted history, not at a presumed contiguous ID sequence. Persist the cursor after saving a page for interruption recovery. [History method](https://core.telegram.org/method/messages.getHistory); [pagination semantics](https://core.telegram.org/api/offsets#offset-id-based-pagination).
- For ongoing additions, record a high-water **channel message ID** and revisit the newest pages, paging back across all new messages (including when more than one page arrived). `min_id` is a strict greater-than filter, but Telegram applies additional filters **after** pagination slicing; it alone is not a safe substitute for traversing a burst larger than one page. `max_id` is strictly less-than, `offset_date` restricts to older messages, and `hash=0` avoids a `messagesNotModified` response during an uncached scan. These cursor rules derive from the [method parameters](https://core.telegram.org/method/messages.getHistory#parameters) and [pagination/filter order](https://core.telegram.org/api/offsets#additional-filtering). This incremental strategy is a design inference, not a Telegram guarantee of a lossless live stream.
- Normal `Message` has `id`, `date`, `message` (text), optional `entities`, `media`, and `edit_date`; selecting text-only content must account for empty-text/service/media messages, and `message` alone does not encode all formatting/link metadata. [Message constructor](https://core.telegram.org/constructor/message). A channel/message-ID pair is the natural identity when storing channel messages: peer IDs and message IDs have distinct scopes. [Peer ID guidance](https://core.telegram.org/api/peers#peer-id).

## Limits, access, and scope of completeness

- Telegram documents `420 FLOOD` and `FLOOD_WAIT_X` as a required wait of **X seconds** before repeating the action; there is **no published fixed `getHistory` requests-per-second allowance** in these method/error docs. Treat the server-specified wait as authoritative, pause the affected work and resume from the last saved page; do not transpose the Bot FAQ's *outgoing-message broadcast* limits onto history reads. [RPC error handling](https://core.telegram.org/api/errors#420-flood); [Bot FAQ: outgoing limits](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this). A takeout export route also documents `messages.getHistory` under `invokeWithTakeout` and special split ranges, but it is a distinct export procedure—not evidence of an unlimited rate or a requirement for a single public channel. [Takeout API](https://core.telegram.org/api/takeout#dialog-and-message-export).
- The user session requires an application `api_id`/`api_hash` (obtained via `my.telegram.org`), plus user authorization; Telegram documents code, QR, and passkey flows, and possible 2FA. This is a prerequisite, **not** a decision about which flow or account to use. [Application registration](https://core.telegram.org/api/obtaining_api_id#obtaining-api-id); [user authorization](https://core.telegram.org/api/auth). Public username resolution does not guarantee that this account can access every post: `getHistory` documents `CHANNEL_PRIVATE` for an inaccessible channel, and posts already removed or outside the account's accessible history cannot be reconstructed from a later history read. [History errors](https://core.telegram.org/method/messages.getHistory#possible-errors); [channel deletion update](https://core.telegram.org/constructor/updateDeleteChannelMessages).
- **No edit/deletion tracking means snapshot semantics.** A historical fetch sees the available *current version* when queried, not the original pre-edit text; later edits and deletions can make locally saved text stale, and an already-deleted post cannot be recovered by a new history scan. Telegram exposes separate channel edit/delete updates and `Message.edit_date`, but processing them is intentionally outside this scope. [Message fields](https://core.telegram.org/constructor/message); [edit update](https://core.telegram.org/constructor/updateEditChannelMessage); [delete update](https://core.telegram.org/constructor/updateDeleteChannelMessages).

**Open questions for an authorized trial:** Does the selected user's session resolve and page all *currently visible* `@brieflyru` history, including earliest posts? What actual page size/flood waits occur for that session? What polling interval and acceptable window of missed posts follow from the desired freshness? Official docs do not promise retention of deleted posts, unchanged text, or a fixed history-read throughput. [History method](https://core.telegram.org/method/messages.getHistory); [error handling](https://core.telegram.org/api/errors#420-flood).
