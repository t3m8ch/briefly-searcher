# UUIDv7 for article identity and ordering

**Answer:** UUIDv7 is a sound surrogate `articles.id` primary key when the requirement is a practically unique ID with useful creation-time index locality. It is **not** a source-publication sort key, a promise of strictly increasing IDs, or an identity that regenerates unchanged after a normalized-table rebuild. Those are separate requirements. [RFC 9562 §§5.7, 6.2, 6.11](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7); [PostgreSQL 18 UUID functions](https://www.postgresql.org/docs/18/functions-uuid.html).

## What the order means

- RFC 9562 §5.7 puts Unix milliseconds in the leading 48 bits; the remaining 74 bits (apart from version/variant) can be random. UUIDv7 therefore sorts **roughly by generation timestamp**; random bits alone cannot order two generations within the same millisecond. RFC §6.11 specifies opaque-byte sorting. Clock rollback, concurrency between independent generators, and equal timestamps rule out inferring a universal strict creation sequence from the format alone. [RFC §§5.7, 6.2, 6.11](https://www.rfc-editor.org/rfc/rfc9562.html#section-6.2).
- Strictly increasing values require a generator with an explicit shared-state/order policy: RFC §6.2 describes optional (1) fixed counter directly after the timestamp, (2) monotonic random counter, and (3) up to 12 bits of sub-millisecond clock precision; precision alone cannot break ties. It calls for rollover handling and checking a new ID against the previous one, including clock rollback cases. **Do not infer that every UUIDv7 generator implements such a policy.** Even one generator's local monotonicity does not establish a global ordering of concurrent article transactions. [RFC §6.2](https://www.rfc-editor.org/rfc/rfc9562.html#section-6.2); [RFC §6.4](https://www.rfc-editor.org/rfc/rfc9562.html#section-6.4).
- PostgreSQL **18** introduced built-in `uuidv7([shift interval])`; its docs describe millisecond timestamp + sub-millisecond timestamp + random and an optional timestamp shift, but **do not promise strictly monotonic output**. `uuid_extract_timestamp()` supports v7 in 18. PostgreSQL **17** documents only built-in `gen_random_uuid()` (v4) and its timestamp extractor supports v1 only; storing `uuid` or generating v7 in application code is still possible on earlier versions. Check deployed major version before specifying `DEFAULT uuidv7()`. [PG 18 release notes](https://www.postgresql.org/docs/18/release-18.html#RELEASE-18-HIGHLIGHTS); [PG 18 functions](https://www.postgresql.org/docs/18/functions-uuid.html); [PG 17 functions](https://www.postgresql.org/docs/17/functions-uuid.html); [PG 18 uuid type](https://www.postgresql.org/docs/18/datatype-uuid.html).

## Consequences for this scraper

- History is ingested newest-to-oldest while new posts may arrive concurrently; articles are created when the **normalizer** handles saved messages. A fresh UUIDv7 records approximately *normalization/ID allocation time*, not Telegram publication time or fetch time. Sorting `articles.id` would group decades-old backfill near today's new articles; after a full rebuild it would group all rebuilt articles near the rebuild date. For published chronology use the chosen source `Message.date` from the article's posts, with an explicit deterministic tie-breaker such as channel message ID; define which part supplies a multipart article's publication date. Telegram's message schema provides distinct `id` and `date`. [Telegram Message](https://core.telegram.org/constructor/message); [RFC §5.7](https://www.rfc-editor.org/rfc/rfc9562.html#section-5.7).
- The plan deletes `posts`/`articles` and replays `raw_posts`. Calling `uuidv7()` again necessarily mints a new *candidate* value, not the previous article ID; `shift` changes its timestamp but does not derive the remaining bits from a source key and does not fix identity. If cross-rebuild links/index document IDs must survive, **persist an article-key → ID mapping outside the cleared tables** and reuse it, or define a canonical immutable source key (including channel identity and a designated post ID) and derive a deterministic name-based ID, e.g. UUIDv5. RFC §6.5 requires equal name + namespace to produce equal UUIDs. A composite article may later gain an earlier part or be merged/split; defining the canonical key and reconciliation policy is necessary before promising identity across such changes. If rebuild stability is not required, a generated UUIDv7 PK plus rebuilding all dependent indexes is consistent with the plan's *within-one-build* stability. [RFC §§5.5, 6.5](https://www.rfc-editor.org/rfc/rfc9562.html#section-6.5); [PostgreSQL 18 UUID functions](https://www.postgresql.org/docs/18/functions-uuid.html); [local scraper plan](../scraper-plan.md).
