# План скрапера Briefly

Цель: собрать доступную историю публичной ленты `@brieflyru`, продолжать получать новые сообщения, сохранить исходные данные для повторной обработки и подготовить статьи как единицы будущего поиска в Tantivy. Это личный учебный проект. В [глоссарии](../CONTEXT.md) различаются сообщение Telegram, текстовый пост, альбом и статья.

Разработка идёт в две части. **Часть 1 — загрузчик**: получает сообщения `@brieflyru` через MTProto и сохраняет их в `raw_posts`. **Часть 2 — нормализатор**: строит из сохранённых сообщений посты и статьи. Его правила и устройство выбираются после анализа загруженной истории; текущие предположения собраны в [гипотезах о нормализаторе](normalizer-hypotheses.md) и решениями не являются.

# Часть 1. Загрузчик

## 1. Получение сообщений

- Использовать пользовательскую MTProto-сессию: [`messages.getHistory`](https://core.telegram.org/method/messages.getHistory) читает историю канала, тогда как [Bot API](https://core.telegram.org/bots/api#getting-updates) выдаёт обновления боту, но не предоставляет полный исторический обход. Потребуются `api_id`, `api_hash` и вход в пользовательский аккаунт. Вход выполняется один раз разовой командой `login`; полученная сессия `grammers` хранится в PostgreSQL (таблица `telegram_session`), а не файлом на диске ([ADR-0002](adr/0002-twelve-factor-app.md)). Секреты и сессию не сохранять в Git, не показывать в логах и веб-админке. Целевой канал `@brieflyru` задаётся конфигурацией и разрешается клиентом Telegram при подключении. Одна БД предназначена только для этой ленты; смена источника требует отдельной БД или очистки собранных данных и курсоров.
- Клиент — [`grammers`](https://github.com/Lonami/grammers). Сообщение сохраняется как JSON, полученный через `serde` из типов `grammers-tl-types` с фичей `impl-serde` (по умолчанию выключена). Форму этого JSON задают версия crate и TL layer, из которого сгенерированы типы; после обновления библиотеки у новых строк могут появиться, исчезнуть или переименоваться поля. Поэтому каждая строка помечается значением `payload_schema`, например `grammers-tl-types 0.x / layer N`. JSON-пути к `grouped_id`, тексту и дате не угадывать, а установить по записанной выборке (шаг 2 порядка реализации).
- **Страница** — ответ одного вызова `messages.getHistory`: до `limit` (не больше 100) сообщений канала, упорядоченных от большего `message_id` к меньшему. Больший ID означает более позднюю публикацию. Параметр `offset_id` — **исключающая верхняя граница**: Telegram берёт сообщения с ID строго меньше `offset_id` и возвращает `limit` самых свежих из них. Значение `0` особое и означает «без границы»: ответ содержит `limit` самых свежих сообщений всего канала, а не все его сообщения. Пример при последнем сообщении канала 50 000 и `limit = 100`: `offset_id = 0` → 50 000…49 901; `offset_id = 49 901` → 49 900…49 801.
- **Проход** — один обход канала от самых свежих сообщений вниз. Он сохраняет все сообщения с ID больше `newest_fetched_id` — наибольшего `message_id`, до которого все сообщения канала уже сохранены. На пустой БД `newest_fetched_id` пуст, поэтому первый проход доходит до начала канала и загружает всю доступную историю; каждый следующий забирает только вышедшее после прошлого прохода. Шаги:
  1. первая страница запрашивается с `offset_id = 0`;
  2. каждая следующая — с `offset_id`, равным наименьшему ID предыдущей страницы;
  3. проход завершается на странице, где встретился ID не больше `newest_fetched_id`, либо на пустой странице — это начало канала, более ранних доступных сообщений нет;
  4. после завершения `newest_fetched_id` становится равным `max(message_id)` в `raw_posts`.

  Пример первого прохода при последнем сообщении канала 50 000: 50 000…49 901, 49 900…49 801, …, пустая страница; итог — `newest_fetched_id = 50 000`. Пример следующего прохода, когда вышли сообщения до 50 150: первая страница 50 150…50 051 — её наименьший ID больше 50 000, нужна вторая; вторая (`offset_id = 50 051`) — 50 050…49 951, на ней есть ID не больше 50 000, проход завершён; итог — `newest_fetched_id = 50 150`.
- Проходы повторяются с интервалом опроса. Новое сообщение канала всегда получает ID больше существующих, поэтому ниже уже сохранённого диапазона ничего не появляется: после первого прохода к началу канала возвращаться не нужно. Сообщения, вышедшие во время прохода, новее его первой страницы и попадут в следующий проход; во время первого прохода они появятся в БД только после его завершения. ID могут иметь пропуски: число сообщений нельзя выводить из максимального ID.
- Состояние прохода не хранится отдельно, а выводится из `raw_posts` и `newest_fetched_id`. Проход сохраняет только сообщения не новее своей первой страницы и идёт вниз без пропусков, поэтому сохранённые сообщения с ID больше `newest_fetched_id` — ровно то, что успел сохранить текущий проход, и они покрывают непрерывный диапазон:
  - **незавершённый проход есть**, если в `raw_posts` есть строки с ID больше `newest_fetched_id` (при пустом `newest_fetched_id` — любые строки);
  - **продолжать его** нужно с `offset_id = min(message_id)` среди этих строк;
  - **его первая страница** начиналась с `max(message_id)` в `raw_posts` — это значение и становится `newest_fetched_id` по завершении.

  Если таких строк нет, следующий проход начинается с `offset_id = 0`.
- Каждая страница сохраняется одной транзакцией PostgreSQL; последняя страница прохода — вместе с обновлением `newest_fetched_id`. При падении до коммита страница запрашивается повторно. При падении после коммита проход продолжается с вычисленного `offset_id`, а не с `offset_id = 0`: для первого прохода это экономит сотни уже сделанных запросов. Сообщение, полученное повторно, не вставляется второй раз благодаря PK `message_id` и вставке без обновления.
- Не задавать «разрешённые Telegram N запросов/с»: такой фиксированной нормы для чтения истории [не опубликовано](https://core.telegram.org/api/errors#420-flood). Ограничить собственный темп и число одновременных запросов. Если Telegram отвечает ошибкой `FLOOD_WAIT_X`, он требует подождать X секунд перед повторением действия: сохранить время окончания ожидания в `flood_wait_until`, прекратить соответствующие запросы до этого времени и показать ожидание в веб-админке. Задержка появления новых публикаций в десятки минут допустима. Не обходить лимиты несколькими аккаунтами.
- Сохранять только текущее доступное содержимое сообщений при первом чтении. Последующие правки и удаления не отслеживать; публикацию, удалённую до обхода, восстановить нельзя. Комментарии связанного обсуждения не читать. Медиафайлы не скачивать.

## 2. Хранилище

Одна PostgreSQL-БД — постоянное хранилище загрузчика и единственный источник данных для будущего нормализатора. Очередь сообщений и отдельный брокер не требуются.

| Таблица | Назначение и ключевые поля |
| --- | --- |
| `raw_posts` | По одной записи на **каждое сообщение Telegram**, включая медиа без подписи: `message_id BIGINT` — первичный ключ для единственного целевого канала; `payload JSONB NOT NULL`; `payload_schema TEXT NOT NULL` — чем записан `payload` (раздел 1); время первого сохранения. Отдельного столбца `channel_id` нет. `payload` — полный декодированный объект Telegram, включая метаданные медиа, но не загруженные файлы; после вставки он не переписывается. Это не оригинальные TL-байты ([ADR-0001](adr/0001-decoded-telegram-payload.md)). Поля учёта обработки (например, `processed_at`) добавит миграция нормализатора, если выбранный в части 2 дизайн их потребует. |
| `ingestion_state` | Единственная запись для настроенного канала: `newest_fetched_id` — наибольший `message_id`, до которого все сообщения канала сохранены; `NULL`, пока первый проход не завершён. Больше курсоров нет: состояние незавершённого прохода выводится из `raw_posts` (раздел 1). `flood_wait_until TIMESTAMPTZ NULL` — срок ожидания после ошибки Telegram `FLOOD_WAIT_X`, чтобы перезапуск не отправил запрос раньше времени. Также хранить время последнего успешного запроса. Отдельные ID канала и флаг «история загружена» не нужны: признак загруженной истории — `newest_fetched_id IS NOT NULL`. |
| `telegram_session` | Единственная запись с сериализованной сессией `grammers` (ключи авторизации, адреса дата-центров, кэш peers). Пишется командой `login` и загрузчиком, когда клиент обновляет сессию. Это секрет: не показывать в веб-админке и логах. |
| `worker_state` | Единственная запись загрузчика: последний heartbeat, текст и время последней ошибки, время следующей попытки. Данные нужны веб-админке и для наблюдения после перезапуска; секреты и сырой `payload` сюда не записывать. |

Сообщения вставляются без обновления (`ON CONFLICT (message_id) DO NOTHING`): повторно полученное сообщение не меняет впервые сохранённый `payload`.

## 3. Веб-админка

Пользовательский интерфейс — локальный сайт, который обслуживает Rust-приложение через loopback, а не интерактивная CLI или TUI. В части 1 админка только читает БД и показывает:

- состояние загрузчика и его последний heartbeat;
- загружена ли история (`newest_fetched_id IS NOT NULL`) и `newest_fetched_id`;
- идёт ли сейчас проход и до какого ID он дошёл (`min(message_id)` среди строк новее `newest_fetched_id`): во время первого прохода это прогресс загрузки истории;
- число сохранённых сообщений в `raw_posts`;
- текущую паузу из-за Telegram (`flood_wait_until`);
- время последнего успешного запроса;
- последнюю ошибку.

Число «43 000+» не использовать как точный знаменатель прогресса: доступная история может отличаться. Сводка обновляется раз в секунду; частота опроса Telegram от частоты обновления UI не зависит.

Сервер отдаёт готовый HTML, JSON API нет; обновление без перезагрузки страницы делает [HTMX](https://htmx.org/). Собственный JavaScript сводится к одному встроенному скрипту. Он переводит времена из UTC в часовой пояс браузера: сервер отдаёт все времена в UTC, без JS они так и показываются с пометкой UTC. Ещё он приостанавливает обновление, пока на странице выделен текст, чтобы замена блока не сбрасывала выделение. Больше логики на клиенте нет ([заметка об админке](research/admin-panel.md#часовой-пояс-решено)).

- `GET /` — страница целиком;
- `GET /status` — HTML-фрагмент со сводкой; страница запрашивает его раз в секунду и заменяет только блок сводки. Если сервер не ответил или вернул ошибку, на экране остаются последние полученные данные.

Данные для обоих маршрутов даёт одна функция crate хранилища — сводка для админки. Файл HTMX хранится в репозитории и отдаётся самим сервером, без CDN. В части 2 изменяющие действия и поиск добавляются тем же способом — маршрутами с HTML-ответами.

Управляющих действий в части 1 нет. Сервер уже в части 1 отклоняет запросы с чужим `Host` — защита от DNS rebinding ([заметка об админке](research/admin-panel.md#доступ-и-безопасность)). Когда в части 2 появятся изменяющие `POST`-действия, к ней добавляется проверка `Origin`: любой открытый в браузере сайт может отправить запрос на loopback-адрес.

## 4. Границы Rust-проекта

Один Cargo workspace. Crates части 1:

- доступ к Telegram: MTProto-клиент и trait `HistorySource` — запрос страницы истории по `offset_id` с ошибкой `FloodWait(секунды)`. Загрузчик зависит только от trait, поэтому тесты подставляют поддельный источник;
- хранение и транзакции PostgreSQL на [`sqlx`](https://github.com/launchbadge/sqlx) с tokio. Это **единственный crate, который обращается к БД**: в нём схема, миграции (`migrations/`, вшиваются в бинарник через `sqlx::migrate!()`) и все SQL-запросы. Загрузчик и веб-сервер вызывают его функции и не пишут SQL сами. Миграции применяет только разовая команда `migrate`; долгоживущие процессы схему не меняют. Миграции части 2 тоже добавляются сюда: у одной БД одна линейная история миграций. Тесты хранилища и загрузчика используют `#[sqlx::test]`: каждый тест получает отдельную чистую БД с применёнными миграциями. Запросы писать макросами `query!`/`query_as!` с проверкой при компиляции; для сборки без живой БД хранить кэш `cargo sqlx prepare` в репозитории;
- приложение: один бинарник с командами `migrate` и `login` (разовые административные) и `loader` и `web` (долгоживущие процессы). Загрузчик и веб-сервер работают **отдельными процессами**; остановка или перезапуск одного не перезапускает другой.

Не создавать отдельные workspaces или crate для каждой таблицы. Crate нормализации появится в части 2 как логика «payload → посты и статьи» без SQL; читает и записывает он через crate хранилища; поисковый crate с Tantivy — после появления проверенных статей: он читает нормализованные статьи и их ссылки, не зависит от сырого формата Telegram.

## 5. Эксплуатация (12-factor)

Приложение следует [12-factor app](https://12factor.net/ru/) ([ADR-0002](adr/0002-twelve-factor-app.md)).

| Фактор | Как выполняется |
| --- | --- |
| I. Кодовая база | Один Git-репозиторий, один Cargo workspace. |
| II. Зависимости | Объявлены в `Cargo.toml`; `Cargo.lock` и кэш запросов `sqlx` хранятся в Git. |
| III. Конфигурация | Только переменные окружения: `DATABASE_URL`, `api_id`, `api_hash`, имя канала, интервал опроса, задержка между запросами, адрес веб-сервера. Локальный `.env` — удобство разработки, в Git не попадает. |
| IV. Сторонние службы | PostgreSQL подключается по `DATABASE_URL`; Telegram — внешний ресурс, адресуемый конфигурацией. Замена БД не требует изменения кода. |
| V. Сборка, релиз, запуск | Сборка бинарника → релиз: бинарник плюс окружение → `migrate` → запуск `loader` и `web`. |
| VI. Процессы | Процессы не хранят состояния между запусками: сообщения, `newest_fetched_id`, `flood_wait_until`, `worker_state` и сессия Telegram — в PostgreSQL; состояние прохода выводится из `raw_posts`. |
| VII. Привязка портов | Веб-сервер сам слушает адрес и порт из конфигурации; по умолчанию loopback. |
| VIII. Параллелизм | Типы процессов — `loader` и `web`. `loader` запускается ровно в одном экземпляре: при старте он берёт session-level advisory-блокировку PostgreSQL на выделенном соединении, второй экземпляр завершается с понятной ошибкой. |
| IX. Одноразовость | Быстрый старт; по SIGTERM/SIGINT загрузчик прекращает работу после текущей транзакции или откатывает её, веб-сервер дорабатывает текущие запросы. Внезапное падение безопасно: состояние выводится только из закоммиченных данных. |
| X. Паритет окружений | Одна и та же PostgreSQL в разработке и тестах (`#[sqlx::test]`), без замены БД на заглушки. |
| XI. Логи | Поток событий в stdout через `tracing`, без файлов логов и без секретов. |
| XII. Административные процессы | `migrate` и `login` — разовые команды того же бинарника с той же конфигурацией. |

## Порядок реализации и проверки части 1

1. Добавить в crate хранилища первую SQL-миграцию `sqlx`, которая на пустой PostgreSQL-БД создаёт `raw_posts`, `ingestion_state`, `telegram_session` и `worker_state`. Проверить только воспроизводимость схемы: применить миграцию к пустой БД командой `migrate`.
2. Войти в аккаунт командой `login` (сессия сохраняется в `telegram_session`), проверить доступ к `@brieflyru` и запросить несколько страниц `messages.getHistory`. Записать ответы как фикстуры в `tests/fixtures/`, включив альбомы и составные статьи из [публичной выборки](research/briefly-multipart-sample.md). По фикстурам установить JSON-пути к `grouped_id`, тексту и дате и значение `payload_schema`.
3. Реализовать проход поверх `HistorySource`. Проверить тестами на поддельном источнике, который отдаёт страницы из фикстур, и тестовой PostgreSQL:
   - первый проход на пустой БД сохраняет все страницы источника до пустой и устанавливает `newest_fetched_id` равным наибольшему ID первой страницы;
   - прерывание до коммита последней страницы прохода оставляет `newest_fetched_id` прежним; следующий запуск снова запрашивает эту страницу, сохраняет её без дублей и завершает проход;
   - новый экземпляр загрузчика поверх БД с незавершённым проходом (первым и очередным) запрашивает `offset_id = min(message_id)` среди строк новее `newest_fetched_id`, а не `offset_id = 0`, и по завершении устанавливает `newest_fetched_id` равным наибольшему ID первой страницы этого прохода;
   - если источник повторно отдаёт сообщение с изменённым текстом, в `raw_posts` остаётся впервые сохранённый `payload`;
   - `FloodWait(n)` на очередном вызове записывает `flood_wait_until`, и до этого срока загрузчик не обращается к источнику;
   - после появления в источнике двух страниц новых сообщений следующий проход сохраняет обе, останавливается на странице с ID не больше `newest_fetched_id`, не запрашивает более ранних страниц и сдвигает `newest_fetched_id` только после сохранения второй;
   - сообщения, добавленные в источник во время прохода, сохраняются следующим проходом.
4. Реализовать веб-админку. Проверить, что при поддельном `FloodWait` страница показывает срок паузы, а после ошибки источника — её текст и время.
5. Запустить загрузчик на реальном `@brieflyru` до исчерпания истории. Проверить: самый старый сохранённый `message_id` совпадает с первой публикацией, доступной в клиенте Telegram; после первого прохода `newest_fetched_id` задан, а следующие проходы не доходят до начала канала; новая публикация канала появляется в `raw_posts` в пределах интервала опроса.

Технические ограничения получения истории и представления данных сведены в [заметке о Telegram API](research/telegram-history.md) и [заметке о TL/JSON](research/telegram-payload.md). Для живой проверки потребуется пользовательская авторизация и доступная PostgreSQL-БД; одни публичные веб-страницы не подтверждают поведение MTProto.

# Часть 2. Нормализатор (набросок)

1. **Анализ.** После загрузки истории агент однократно исследует `raw_posts` запросами только на чтение по [вопросам из гипотез](normalizer-hypotheses.md#вопросы-для-анализа). Результат — `docs/research/briefly-normalization-analysis.md` и размеченные положительные и отрицательные примеры для фикстур нормализатора. В рабочем пайплайне агент не вызывается.
2. **Решения.** По итогам анализа выбрать устройство нормализатора (инкрементальная очередь или полный пересчёт), схему `posts`/`articles` и правила склейки частей; значимые решения оформить ADR, уточнить глоссарий.
3. **Реализация.** Нормализатор, расширение веб-админки, затем поиск.
